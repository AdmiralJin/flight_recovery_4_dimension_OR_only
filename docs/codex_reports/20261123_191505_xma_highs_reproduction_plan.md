# 厦航 HiGHS 全量首解复现计划

2026-11-23 19:15（北京时间）

## 项目与起点

本仓库是航班受扰恢复研究平台，包含 AIR、厦航和公开基准三条路线，共用 Workbench v3。本次聚焦厦航天池数据上的航班执行与取消、飞机调配、旅客改签。模型与独立审计在 `backend/business/xma/`，批次由 `scripts/xma_first_solution.py` 启动，可直接从命令行复现。

本次已核对分支 `feature/xma-highs-first-solution` 和基准提交 `8927c281`，运行 `python VERIFY_XMA_TRANSFER.py` 通过，覆盖 585 个补充包文件和 91 个 Git 数据文件。当前命令行使用 Python 3.13.9。本机可见物理内存约 63.3 GiB，检查时可用约 48.9 GiB，正式运行前需重新测量。此次工作止于项目核查与计划制定。

旧批次 Q1（598 班／36 架）和 H1（1176 班／71 架）已有独立审计通过的条件子集方案。FULL（2364 班／142 架）在固定原飞机的辅助模型阶段运行约 10.3 分钟后触及系统可用内存下限，尚无完整方案。旧批次保留作对照，新实验从本机校准开始。

## 目标与固定口径

第一里程碑是取得 FULL 的首个完整、独立审计通过的可行方案，第二里程碑才是降低同口径的天池目标值。固定 HiGHS、`joint_arc_flow`、`tianchi_2017`、30 分钟基础网格及规则边界，国内／国际最长延误分别为 1440／2160 分钟，恢复截止为北京时间 2017-05-10 21:40。沿用厦航模型的机组、维修关闭设置。

## 执行顺序

| 阶段 | 工作 | 进入下一步的条件 |
| --- | --- | --- |
| 1. 对齐环境 | 在 Windows 上使用独立的 64 位 Python 3.12.4 环境，按 `requirements.txt` 安装依赖。核对 HiGHS 1.15.1、gurobipy 13.0.3，做一次建模与 HiGHS 求解的小实例检查。 | `python -m pip check` 通过，gurobipy 建模环境能启动，求解记录确认使用 HiGHS。 |
| 2. 打通内存配置 | 在批次控制器 `backend/benchmarks/xma_first_solution.py` 和首解搜索 `backend/business/xma/search.py` 共用一份资源配置。按运行前可用内存预留系统余量，由进程树硬上限推导内部预测准入额度，初始采用 70% 比例。同步更新冻结清单、worker 传参、Windows 守护器调用、峰值判停与日志，并复核启动门槛和系统紧急下限。 | 用非默认值验证从清单到实际 worker、守护器和结果的数值一致；覆盖预测超限与默认配置回归。当前代码分别写死了 6 GiB 硬上限、4.8 GiB 准入线，另有独立的 4 GiB 启动门槛。 |
| 3. 本机短校准 | 在全新目录运行 `pilot`，检查 20／50／100 班回归和扩大延误范围的小样本；记录目标、审计、预测内存、实测峰值及校准因子。 | 本机 `calibration.json` 中 `passed=true`。若校准涉及的源码发生变化，重做 pilot。 |
| 4. 冻结并运行 FULL | 建议本轮显式实现并测试仅选 FULL 的任务选项，在 `prepare` 时将选择和预算写入清单，保留默认 Q1／H1／FULL 串行行为（6／12／24 小时）。用新的时间戳目录，依次执行 `prepare --calibration <本机校准文件>`、`verify`、`run --start-now`，各命令按 CLI 指定批次目录。 | 启动前核对输入覆盖 2364 班／142 架、源码与输入哈希一致、任务选择与资源策略正确。运行期间监看进程树峰值、系统余量、阶段事件与首个检查点。 |
| 5. 验收并改进 | 核对汇总、FULL 结果及对应 attempt 的完整产物，锁定首解；随后只在相同输入和评分口径下比较目标值。如已安装 Java，可另做官方 JAR 复核。 | 按下列标准记录首解及后续改善。 |

## FULL 验收与失败处理

- `summary.json` 的 `full_solution=true`，且 FULL 的 `audit_pass=true`、`complete_decisions=true`。核对 `checkpoint.json`、独立审计记录和 `flights.csv`，确认 2364 个输入航班各有唯一决策，飞机归属和连续性按 142 架全量机队核验。
- 报告首次审计通过的用时、目标值和峰值内存。下界或 Gap 缺失时留空，仅在有全局最优性证明时标注最优。
- 若预算耗尽仍无完整方案，从 `events.jsonl`、`worker.log` 和 FULL 结果定位最后阶段，区分预测准入拒绝、进程树触顶、系统可用内存过低和求解超时。针对原因调整资源或模型构建并另建批次；保留每轮记录与检查点。
