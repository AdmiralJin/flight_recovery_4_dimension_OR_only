# 厦航 HiGHS 首解详细实施计划

计划冻结时间：2026-11-19，北京时间。根据同日 16:12 版计划和用户确认制定。

## 计划摘要

在 Workbench v3 上使用显式 HiGHS、`joint_arc_flow` 和 `tianchi_2017`，优先争取覆盖 2364 航班、142 飞机并通过完整业务审计的恢复方案，再改善目标。先提交现有三份文档，再创建 `feature/xma-highs-first-solution` 开展工作。

已确认：取消人为 120 分钟限制，保留官方国内 24 小时、国际 36 小时；允许固定原机尾及逐步扩大换机集合的辅助联合模型；本机全量合法首解优先，完整模型资源不足时允许完整模型 LB、Gap 暂缺。

顺序：冻结规则和分组 → 等价压缩衔接结构 → 运行中审计和保存 → 小例验证 → Q1（6 小时）→ H1（12 小时）→ FULL（24 小时）。三项串行，总预算 42 小时；等待资源不计时。辅助模型并非 AIR 分解，不拆开旅客、飞机和机场业务约束。

## 计划详情

### 1. 问题定义与接口

- 全量：2364 航班、142 飞机、79 机场、773 转机、616 联程、11 扰动、6 关闭规则。
- 原调整窗口：2017-05-06 06:00 至 2017-05-09 00:00（含边界）。窗外固定，原机尾前缀和后缀仍约束衔接。
- 全局恢复截止：2017-05-10 21:40+08:00，取全量可调整航班在官方延误上限内的最晚到达时刻，不扩大调整窗口。
- 30 分钟网格，补源规则精确边界和航班延误终点。仅执行延误、取消、同机型换机和改签，不新增提前、调机、跨机型换机、拉直、机组、维修。
- 保留关闭、台风、流量、停机、禁飞航线、飞机连续性、短过站、联程、物理座位、转机、改签和按机型及机场汇总的期末飞机平衡。
- `maximum_delay_minutes` 和 `max_assignment_options` 支持 null。前者 null 表示仅保留官方上限，后者 null 表示不按分配数拒绝；旧默认值及数值语义保留。
- 新增可选 `recovery_end`。辅助搜索配置、问题指纹和界作用域单独记录；正式模型不删除合法换机候选。
- 更新 v3 校验、提示、时间范围、导入导出；直接路线不展示分解专用参数。

### 2. 分组和边界

- 完整机尾分四组，配额为 36、35、36、35；H1=Q1+Q2，H2=Q3+Q4，各 71 飞机。
- 航班 73 所在机尾先入 Q1。其他按受扰航班数、链长度降序，机尾号打破平局。
- 在未满额组中，最小化加入后机型数、航班数、受扰航班数的标准化平方偏差增量，等权，组号打破平局。
- 冻结实际清单、源哈希、分组哈希和边界清单。首轮三项；其余组只登记，不自动加跑。
- 组外转入组内的航班原时刻固定；转向组外的影响列出但不计子集目标；源机场容量不缩放，不宣称已扣除外部占用。
- 当前联程均同原机尾，检查无遗漏。子集仅是条件研究问题，不拼接为全量方案。

### 3. 模型结构和首解策略

放宽至官方延误范围的只读核算：72984 候选、6467198 分配、47665654 显式联程/短过站衔接；相关变量至少 73607430，尚不含地面与旅客。本机约 16 GiB，不直接照旧构模。

- 用同机尾、指定前后航班对的专用时间通道替代候选两两连接。左段过站后进入，右段在合法时刻离开，只接指定航班；联程直接相邻通过实际通道流量识别。禁止借共享节点误接其他航班。
- 压缩保持整数业务可行集和目标；用小例旧表示及全路径 Oracle 对拍。
- 预检和构模复用结构，减少 Python 字典、网络和矩阵副本；不删除航班、需求、正式候选。
- 先固定原机尾，在生成网络前限制分配。最多 min(600 秒，总预算 10%)。
- 无首解则按同机型、初始机场、机尾号排序，构成大小 2、4、8、16……的嵌套换机集合；每级最多 min(1800 秒，剩余预算一半)，资源检查后运行。
- 每级仍为包含全部航班、旅客及业务约束的 HiGHS 联合 MIP。找到方案即审计保存，通过部分 MIP 起点传入更大范围，不把起点固定为约束。
- 完整合法换机范围通过资源门槛则运行；否则剩余时间改善最大可承载范围。切换释放旧模型，全阶段共享预算。
- 辅助合法方案可作完整问题 UB；辅助不可行、LB、最优仅属于其受限范围。

### 4. 运行中保存与计时

- HiGHS 改善解回调读取 `mip_solution`，用冻结列索引提取 x/u/整数改签，不在回调查询求解器解，不复制全模型字典。
- 首个候选立即审计，后续最多每 5 秒审计一次；最终解和退出时再检查。审计及模型评分一致后原子保存。
- 审计失败或评分冲突保留诊断并停止该次运行，保留此前合法检查点。
- 检查点含输入和问题指纹、搜索范围、决策、评分、审计、时间、有效界来源。
- 分别记录首次求解器候选、首次审计通过、首次落盘；预检零目标解不计业务首解。
- 停止先软中断，120 秒收尾；硬终止后监护恢复最后一个完成的合法检查点。

### 5. 验证与资源

- 验证官方延误、截止、关闭端点、冻结规则、航班 73 候选、联程和短过站、压缩前后可行性和最优目标一致。
- 测试回调结束前保存、评分一致、超时/取消/异常恢复、MIP 起点、明确后端及无静默回退。
- 回归旧 30/65/103 航班的冻结配置；v3 走通导入、预检、运行、停止、展示、导出。
- 单线程、随机种子 0、MIP Gap 目标 0；进程树硬上限 6 GiB，预测峰值大于 4.8 GiB 不派发该范围。
- 启动可用内存至少 7.5 GiB；运行可用内存低于 1.5 GiB 持续 10 秒则请求收尾。等待不耗预算，不杀其他用户程序。
- 小例实测校准内存估计，保存预测和实测。资源受限是结果，不等于业务不可行。
- Q1→H1→FULL，小例限时无解不挡大例，审计/代码/数据完整性失败先修。

### 6. 交付与判定

- 首要验收：2364 航班全部有决策，完整业务审计通过，目标复算一致，保存决策、CSV 和旅客账本，记录首解时间和运行范围。
- 完整 LB 只取同一候选问题的有效完整模型界；缺失则 null，Gap 也 null。无方案指标不显示零。
- 最优需完整模型审计通过且有效界闭合；结论限于 30 分钟网格加源边界，不是连续时间最优。
- 辅助不可行不代表完整不可行，必要条件可行不代表有完整方案，超时无解不代表不可行。
- 保存新批次输入、代码、环境、分组、配置哈希；每次尝试独立目录，含模型规模、日志、事件、检查点、结果、审计、LB/UB/Gap、耗时、资源峰值和原因。旧批次不改写。
- 全量首解尝试随附 Java 评分器复核；没有可用 Java 或未完成则标未外部认证，不虚报。
- 每次工作完成在 `docs/codex_reports` 生成精简时间戳报告，首先回答是否有全量合法解、目标、耗时和保存位置。
