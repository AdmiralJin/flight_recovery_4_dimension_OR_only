# AIR 航班恢复工作台用户使用指南

本文面向使用浏览器工作台开展航班恢复研究、方案核验和结果审计的用户，说明如何启动系统、建立研究草稿、检查扰动、运行求解、阅读图表、比较方案并导出审计材料。

当前默认界面是 **Workbench v2**，访问地址为 `http://127.0.0.1:8000/workbench-v2/data`。根地址 `http://127.0.0.1:8000` 在前端已构建时会自动进入该界面。`/legacy` 是旧版兼容入口，不建议在同一次研究中混用两套界面。

> 使用边界：本系统是单机研究与审计工具，不是航空公司生产运行控制系统。页面中的传播风险不是因果结论，求解结果也只在当前输入、候选范围、规则和求解状态下成立。

## 1. 开始前准备

建议使用桌面版 Chrome 或 Edge。手机和平板可用于查看运行状态、图表和摘要，但复杂 JSON 编辑更适合桌面端。

运行求解时优先使用 Gurobi；厦航模型超过当前 Gurobi 许可证规模时，会自动切换到原生 HiGHS。即使首选求解器不可用，仍可进行数据查看、草稿编辑、编译预览和部分可视化。页面顶部会显示求解器状态。

首次使用时，在项目根目录 `D:\python_project\flight_recovery` 打开 PowerShell，依次执行：

```powershell
python -m pip install -r requirements.txt
cd frontend
npm install
npm run build
cd ..
python -m uvicorn backend.main:app --reload
```

后续启动通常只需在项目根目录执行：

```powershell
python -m uvicorn backend.main:app --reload
```

然后访问：

```text
http://127.0.0.1:8000
```

注意事项：

- 不要直接双击 `frontend/index.html`。工作台需要 FastAPI 提供接口和静态资源。
- 修改 React 前端代码后，需要重新执行 `npm run build`。
- 如果构建产物不存在，根地址会退回旧界面；此时应先完成前端构建。
- 关闭浏览器不会停止已经提交的求解任务。
- 关闭后端服务会中断正在运行的任务；重启后该任务会显示为 `interrupted`。

## 2. 认识工作台

左侧导航按照实际工作顺序分为六个页面：

1. **数据设计**：选择内置 Case、创建草稿、检查或修改数据。
2. **扰动影响**：编译草稿，检查有效容量、候选规模、直接暴露和传播风险。
3. **求解**：创建不可变快照，提交任务，查看上下界、Gap 和结构化事件。
4. **可视化**：查看航班、飞机、机组、旅客、容量、传播、成本和延误图。
5. **方案对比**：在 Original、Impact、Recovered 和 Delta 四种语义下核对方案。
6. **审计**：查看运行证据，并导出包含输入、结果和 Trace 的完整审计包。

顶部区域包含：

- **当前工作草稿**：切换已经创建或导入的草稿。每个选项同时显示来源类型和工作副本短 hash，用于区分同名草稿。
- **工作副本 hash**：草稿内容的短哈希，用于识别当前版本。
- **校验**：显示待编译、通过或有错误。
- **求解器**：显示 Gurobi 是否可用。
- **运行**：显示当前任务状态。
- **浅色或深色主题**：点击右上角主题按钮切换；选择保存在当前浏览器中，不影响研究数据。

系统将草稿、快照、运行和结果保存在项目根目录的 `.workbench/` 中。内置 Case 始终只读，用户编辑发生在克隆或导入的草稿中。

## 3. 推荐的完整操作流程

```text
选择只读 Case
→ 克隆为草稿
→ 检查或修改数据并保存
→ 编译并预览扰动影响
→ 创建不可变快照并求解
→ 查看可视化和方案对比
→ 导出审计包
```

### 第一步 选择 Case 并创建草稿

1. 打开“数据设计”。首次进入时，系统会显示内置 Case 库。
2. 阅读 Case 的分类、说明和标签。
3. 点击所需 Case 右侧的“克隆为草稿”。
4. 等待顶部提示“已克隆为草稿”。
5. 确认顶部“当前工作草稿”显示新草稿名称、`Case 克隆` 来源和短 hash。

需要改用其他基线时，点击页面右上角“克隆内置 Case”重新打开 Case 库。克隆操作不会修改原 Case，也不会覆盖已有草稿。

如果系统中已有草稿，启动后通常会自动选择草稿列表中的第一项。可以使用顶部下拉框切换草稿；切换后页面会返回“数据设计”。

“克隆内置 Case”负责从只读基线创建新草稿；“导入草稿”负责从 `.draft.json` 文件创建新草稿；顶部下拉框只在已经存在的草稿之间切换。文件导入、厦航导入、Case 克隆和历史草稿会显示不同来源标签。

### 第二步 检查和编辑数据

“数据设计”页按实体展示当前工作副本：

| 标签 | 主要内容 |
|---|---|
| 航班计划 | 航班、机场、计划起降时间等 |
| 机场 | 机场基础信息 |
| 飞机 | 飞机、机型、初始位置等 |
| 机组 | 机组、资质和初始状态等 |
| 旅客 | 旅客组、行程和人数等 |
| 旧扰动 | 兼容旧 Case 的扰动描述 |
| 类型化扰动 | v2 编译器使用的规则化扰动 |
| Flight Options | 航班原计划、延误、取消等候选 |
| Passenger Itineraries | 旅客运输和未服务候选 |
| 剩余容量 | 各航班候选可使用的剩余座位 |
| 成本 | 当前 Case 的成本覆盖值 |
| Profiles | 求解所引用的配置 ID |

编辑步骤：

1. 选择一个实体标签。
2. 在表格中选择一行。
3. 在右侧“记录检查器”中修改 JSON。
4. 如需撤销或重做编辑器内的修改，使用检查器顶部按钮。
5. 点击“保存工作副本”。
6. 等待“工作副本已原子保存；派生编译状态已失效”的提示。

保存时需要注意：

- JSON 必须语法正确，字段类型必须符合 Schema。
- 记录标识字段应保持唯一，例如 `flight_id`、`tail_id` 或 `option_id`。
- 保存会生成新的工作副本 hash；此前的编译预览不再代表当前草稿。
- 不要只在编辑框中修改而不点击“保存工作副本”。未保存内容不会进入编译或求解。
- 右侧检查器可以折叠。屏幕较窄时，检查器会移动到表格下方。

页面右上角还提供：

- **导入草稿**：导入完整的 v2 草稿 JSON，并创建一个新草稿。
- **导出**：下载当前 `DraftDocument`，文件名以 `.draft.json` 结尾。

这里的导入对象是完整草稿文档，不是旧版的裸 Scenario、Solve Bundle 或审计包。

### 第三步 编译并检查扰动影响

1. 打开“扰动影响”。
2. 点击“编译并预览”。
3. 查看编译摘要：编译状态、直接暴露、传播风险和容量区间变化。
4. 在时空网络中选择航班，结合右侧“编译证据”核对问题。
5. 如果状态为 `Blocked`，按问题中的 `code`、说明和字段路径返回“数据设计”修正。
6. 修改并保存草稿后，再次执行“编译并预览”。

编译通过时状态显示 `Ready`，表示：

- 当前字段、引用关系和候选输入满足快照创建条件；
- 有效容量和候选输入已绑定到当前草稿 hash；
- 可以继续创建求解快照。

`Ready` 不表示数学模型一定可行，也不保证能够得到最优解。模型仍可能返回 `infeasible` 或 `not_converged`。

扰动颜色的含义：

- **直接暴露**：航班直接命中一条可核对的扰动规则。
- **传播风险**：航班通过飞机、机组或其他资源序列与直接暴露航班关联。
- **正常**：当前编译证据中未标记为直接或下游暴露。

这些标记只描述输入暴露和资源链风险，不表示“某个扰动导致求解器选择了某项恢复动作”。

### 第四步 创建快照并运行求解

1. 打开“求解”。
2. 从页面顶部选择运行 Profile。通常使用 `Default exact`。
3. 点击“创建快照并求解”。
4. 系统会自动重新编译当前草稿。
5. 编译通过后，系统创建不可变快照并将任务入队。
6. 在指标区查看任务状态、当前阶段、已用时间、实际求解器、当前最佳解、下界和 Gap。
7. 在阶段时间轴中确认候选生成、模型构建、优化和审计进度。
8. 在按实际耗时绘制的收敛轨迹中观察真实界变化；尚无可行解时，页面会显示候选、变量和约束规模。
9. 在右侧“结构化事件”中查看阶段、迭代、列、割、节点和审计事件。

快照是一次运行的固定输入。运行开始后继续修改草稿，不会改变已经入队的任务。当前实现最多同时运行一个求解任务，其他任务会保持 `queued`。

运行时可以刷新页面或暂时关闭浏览器，后台子进程会继续执行。重新打开工作台后，从“运行历史”选择相应 Run 即可继续查看。

需要停止任务时点击“取消”：

- 系统先请求协作式取消；
- 若求解进程在约 5 秒内未响应，系统会终止隔离进程；
- 已记录的 Trace 会保留；
- 已进入终态的任务不能再次取消。

### 第五步 选择并复查历史运行

“运行历史”中的每一行显示 Run ID 缩写、Job 状态、Optimization 状态和输入 hash。

点击一条运行记录后：

- 求解页切换到该运行；
- 对于终态运行，系统加载 canonical comparison 和审计信息；
- 系统同时回载已持久化的结构化事件，并恢复可用的 LB、UB 和 Gap 轨迹；
- “可视化”“方案对比”和“审计”页随后以该运行的不可变快照为数据源。

页面会显示最近五次本次 incumbent 改进，以及相同研究问题的最近历史结果。没有真实 incumbent 或下界时，系统只显示阶段、耗时、模型规模和心跳，不会生成虚假收敛点。

如需确认结果是否对应预期输入，应比较运行的 input hash，而不是只看草稿名称。

### 第六步 查看运营可视化

打开“可视化”，先在右上角选择数据源：

- **当前草稿 / 编译预览**：用于检查工作副本和扰动影响。
- **历史 Run**：用于查看与该次不可变快照绑定的输入和结果。

页面提供八类图表：

| 视图 | 用途 |
|---|---|
| 航班时空图 | 在机场与时间轴上核对航班计划和恢复位置 |
| 飞机甘特 | 核对飞机轮转和恢复分配 |
| 机组甘特 | 核对机组执行序列 |
| 旅客行程 | 核对旅客运输、改签或未服务状态 |
| 容量热力图 | 按机场和时间区间查看起飞或到达容量 |
| 传播链 | 查看直接暴露与资源序列传播关系 |
| 成本 | 查看目标函数分量 |
| 延误 | 查看起飞和到达延误分布 |

四种语义模式：

- **Original**：原始计划。
- **Impact**：有效扰动和风险暴露，不包含恢复决策。
- **Recovered**：求解得到的恢复计划。
- **Delta**：恢复方案相对原计划的变化。

成本和延误采用更严格的模式语义：Original 显示零基线；Impact 不生成恢复成本或实际延误，因此显示“不适用”；Recovered 显示求解结果；Delta 显示相对 Original 的增量。系统不会在 Impact 下重复展示 Recovered 数据。

系统会禁用当前数据源无法支持的模式或图层。例如非 optimal 运行、缺少完整选中列产物的历史运行，可能不能显示 Recovered 或某些资源恢复明细。将鼠标停在禁用按钮上可查看原因。

可用筛选包括实体、机场、Changed 或 Unchanged、暴露类型，以及容量视图中的起飞或到达方向。选择图中实体后，右侧证据栏显示跨图一致的原计划、暴露、恢复资源和规范化数据。筛选条件与选择对象会写入页面地址，便于刷新后保持当前视图。

### 第七步 对比恢复方案

打开“方案对比”。如果页面提示“尚无对比模型”，先回到“求解”选择一个已完成或其他终态运行。

操作建议：

1. 使用顶部 Original、Impact、Recovered、Delta 切换全页语义。
2. 查看航班总数、Changed 和 Unchanged 数量。
3. 在“航班网络”中按全部、仅 Changed 或仅 Unchanged 筛选。
4. 点击航班查看原计划字段、暴露规则、恢复字段和变化标签。
5. 切换飞机轮转、机组任务、旅客行程、容量、成本和延误进行交叉核对。

航班会被完整划分为 Changed 或 Unchanged。Changed 可同时包含取消、时刻、起降机场、飞机和机组等多个变化标签。`Recovered` 按钮只有在服务端确认恢复层可用时才可点击。

### 第八步 审计并导出

打开“审计”，确认页面顶部的 Run ID、Input hash、Job 状态和 Optimization 状态。

左侧章节包括：

- `summary`：Expected 对拍、目标函数、恢复动作数、Trace 数和诊断。
- `input`：本次运行的完整 Solve Request。
- `decisions`：选中决策与恢复动作。
- `objective`：目标分量和上下界。
- `constraints`：集成约束审计；明细程度取决于本次 Trace 和结果。
- `trace`：完整结构化事件。
- `environment`：运行元数据和环境信息。

点击“导出完整审计包”会下载 `air-recovery-{run_id}.json`。审计包包含运行记录、不可变快照、方案对比、可视化模型、审计信息和事件，适合留档和复现核验。

审计页始终使用所选运行的快照，不会把后来修改的当前草稿混入解释。

## 4. 厦航研究数据专项流程

“数据设计”页顶部提供“厦航数据与求解配置”。该区域用于项目内厦航工作簿或同结构 `.xlsx` 文件的研究性导入。

### 4.1 导入数据

1. 选择研究规模：约 20、100、500 航班或全量。
2. 使用“读取项目厦航数据”读取仓库内置工作簿，或点击“上传厦航工作簿”。
3. 等待预览显示航班数、飞机数和联程数。
4. 确认研究子集说明后，点击“使用此预览创建新草稿”。未读取预览时，也可以直接点击常驻的“创建厦航研究草稿”，系统会按当前固定规模读取并创建。

子集会保留整架飞机航线；外部进港中转航班按原时刻固定。子集评分只针对该研究子问题，不能直接当作全网方案评分。

如需随机研究样本：

1. 在“随机目标航班数”中输入希望研究的约航班数。
2. 随机种子可留空；每次点击“随机抽取”都会自动产生新种子。
3. 系统先随机选择受台风影响的完整机尾航班串，再随机补充其他机尾，因此实际航班数可能略高于目标值。
4. 预览会显示实际航班数、种子和样本标识。“复制种子”用于记录，“使用此种子重建”可重新生成相同样本。
5. 上传的厦航工作簿同样可以随机抽取；页面会标明当前数据来源。

### 4.2 配置厦航求解

厦航草稿可配置：

- **目标函数**：天池评分，或独立研究使用的 AIR 线性成本。
- **算法**：直接联合优化、显式航班串基准、Benders 加联合子问题、Benders 加列生成和分支定价。
- **延误步长**：延误候选的时间网格。
- **最大延误**：单航班允许生成的最大延误范围。
- **求解时限**：本次厦航求解的时限。
- **飞机分配规模上限**：控制候选分配规模。

修改参数后页面显示“有未保存的求解配置”，点击常驻的“保存求解配置”一次性保存所有字段。“另存为新研究草稿”会保留当前草稿并创建副本。即使忘记手动保存，点击“创建快照并求解”时系统也会先提交待保存配置，再用新 hash 编译和创建快照；发生 hash 冲突时不会使用旧参数运行。

当前厦航研究模式的边界包括：机组恢复关闭、座位随飞机分配、两套目标函数彼此独立。不同目标函数的数值不能直接横向比较。

### 4.3 查看和导出厦航结果

厦航运行结束后，“求解”页下方显示：

- 使用的目标函数及总成本；
- 最优、未收敛或当前候选无可行解等状态；
- 各航班实际座位、占座、原旅客驻留、改签送出、改签接收、未服务、进港取消和中转失败；
- 逐项评分和独立审计。

事件栏会记录研究问题、候选生成、模型规模和实际求解器。如果 Gurobi 因许可证规模限制而回退到原生 HiGHS，页面会显示明确的 `solver_fallback` 事件。原生 HiGHS 会通过 `mip_progress` 提供可获得的 incumbent、dual bound、Gap、节点数和求解器耗时；长时间没有界变化时只发送心跳。兼容兜底路径无法提供中间界时，页面会明确说明，不会把心跳画成收敛点。

存在可导出的 incumbent 时，可点击“导出天池 11 列结果”。人数按航段评分口径展示。

## 5. 状态和指标说明

### 5.1 Job 状态

| 状态 | 含义 |
|---|---|
| `queued` | 已入队，等待单并发运行槽 |
| `preparing` | 正在准备输入或子进程 |
| `running` | 求解器正在运行 |
| `completed` | 任务正常结束；仍需查看 Optimization 状态 |
| `failed` | 任务因输入外故障或运行异常失败 |
| `cancelled` | 用户取消，可能保留部分 Trace 或 incumbent |
| `interrupted` | 服务停止等外部原因导致运行中断 |

### 5.2 Optimization 状态

| 状态 | 含义 |
|---|---|
| `optimal` | 在当前正式模型和候选范围内证明最优 |
| `infeasible` | 当前模型和候选范围内无可行解 |
| `not_converged` | 在限制内未闭合最优性；可能存在可用 incumbent |
| `aborted` | 优化过程被取消或中止 |

`completed` 只表示任务执行完成，不等同于 `optimal`。`infeasible` 和 `not_converged` 是正常的优化结果类型，不应自动当作 HTTP 或程序故障。

### 5.3 Bound 和 Gap

- **Lower bound**：当前已证明的目标下界。
- **Upper bound**：当前最好可行解的目标值。
- **Absolute gap**：上下界之差。
- **Relative gap**：相对差距；趋近 0 表示界逐渐闭合。

只有在上下界语义有效时才应解释 Gap。页面没有数据时显示 `—`，不会用模拟百分比代替真实求解事件。

### 5.4 Hash 和数据一致性

- **Working hash**：当前草稿内容版本。
- **Compiled hash**：编译得到的规范化求解输入版本。
- **Input hash**：不可变运行快照的求解输入版本。

任何已保存的输入修改都会产生新的 Working hash，并使旧编译预览失效。历史运行仍绑定原 Input hash，不会因当前草稿变化而改变。

## 6. 导入和导出文件的区别

| 操作 | 文件内容 | 能否再次导入 |
|---|---|---|
| 数据设计页“导出” | 当前完整 v2 草稿文档 | 可通过“导入草稿”创建新草稿 |
| 数据设计页“导入草稿” | 完整 `DraftDocument` JSON | 是 |
| 审计页“导出完整审计包” | Run、Snapshot、Comparison、Visualization、Audit 和 Events | 用于审计留档，不是草稿导入格式 |
| 厦航“上传工作簿” | 约定结构的 `.xlsx` | 经预览后创建厦航草稿 |
| 厦航“导出天池 11 列结果” | 天池口径 CSV | 结果提交或外部分析用途 |

不要将旧版的 Scenario JSON、Solve Bundle、`Export Current Case` 文件或 v2 审计包直接交给“导入草稿”。这些对象的层级和用途不同。

## 7. 常见问题

### 打开根地址后进入旧界面

通常是 React 构建产物不存在。进入 `frontend` 目录执行 `npm install` 和 `npm run build`，然后重新启动后端并访问 `/workbench-v2/data`。

### 页面顶部显示求解器不可用

数据编辑和编译仍可使用。若要运行求解，请检查 Gurobi 安装、Python 包、许可证和页面或 `/api/health` 返回的原因。

### 已修改记录，但编译仍使用旧数据

确认已点击“保存工作副本”，并看到 hash 变化。编辑器中的未保存文本不会进入编译。

### 编译 Ready，为什么求解仍然 infeasible

编译只确认字段、引用、容量和候选输入满足创建快照的条件，不执行完整优化可行性判定。`Ready` 与 `infeasible` 可以同时成立。

### 为什么 Recovered 或某个图层不可用

可能原因包括：尚未选择终态运行、结果不是 optimal、运行没有完整恢复产物，或该历史产物缺少飞机、机组或旅客明细。界面会给出具体降级原因。

### 修改草稿后，历史结果会不会被覆盖

不会。历史运行绑定不可变快照和 Input hash。新修改只影响当前草稿以及以后创建的快照。

### 浏览器刷新后求解会不会停止

不会。任务在后端隔离子进程中运行。刷新或短暂断线只会中断页面连接，重新选择运行即可恢复查看。

### 为什么任务一直 queued

当前最多同时运行一个任务。等待前一个任务进入终态，或按需要取消前一个运行。

### 取消后为什么没有立即停止

系统先给求解过程协作式退出的机会。若约 5 秒内仍未响应，才终止隔离进程并保留已经写入的 Trace。

### 为什么 Impact 中的传播链不能解释恢复动作

传播链是基于输入规则和资源序列构建的风险证据，不是优化器决策的因果模型。恢复动作应结合 Recovered、Delta、目标函数、约束审计和 Trace 解释。

### 如何确认导出的结果可复现

记录 Run ID 和 Input hash，并从“审计”导出完整审计包。该文件包含不可变输入快照、结果、对比模型、事件和环境元数据。

## 8. 旧版界面兼容说明

旧版入口为：

```text
http://127.0.0.1:8000/legacy
```

旧界面包含 Data、Visualization、Recovery、Costs 和 Constraints，并使用 Current Case、revision 和同步求解等旧合同。它主要用于兼容既有测试和旧流程。

以下功能不要与 v2 混淆：

- 旧版 `Import Scenario` 和 `Import Solve Bundle` 不等于 v2“导入草稿”。
- 旧版 `Export Current Case` 不等于 v2“导出完整审计包”。
- 旧版 `STALE` revision 机制在 v2 中由工作副本 hash、compiled hash 和不可变快照替代。
- 旧版 Costs 和 Constraints 页面只适用于 `/legacy`；v2 将成本和 Profile 放在“数据设计”，将运行审计放在“审计”。

新研究任务建议始终从 Workbench v2 开始，并在同一套草稿、快照和运行记录中完成全过程。

## 9. 推荐的结果核验清单

在正式留档前，依次确认：

- [ ] 当前草稿名称和 Working hash 正确。
- [ ] 编译状态为 Ready，且没有未处理的阻断问题。
- [ ] 直接暴露、传播风险和容量变化符合研究场景。
- [ ] 所选运行的 Input hash 与目标快照一致。
- [ ] Job 和 Optimization 状态已分别解释。
- [ ] LB、UB 和 Gap 与 Trace 事件一致。
- [ ] Original、Impact、Recovered 和 Delta 没有混用。
- [ ] Changed 航班及其全部变化标签已经核对。
- [ ] 飞机、机组、旅客、容量和成本图层的可用性已经确认。
- [ ] Expected 对拍、目标分量和约束诊断已经查看。
- [ ] 完整审计包已经导出并与 Run ID 一起归档。
